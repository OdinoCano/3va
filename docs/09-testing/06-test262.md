# test262 (conformance ECMA-262)

## Cómo correrlo

```
./scripts/setup-test262.sh                 # clona tc39/test262 en tests/test262/ (gitignored)
cargo test -p vvva_test --test test262 -- --ignored --nocapture
```

El runner vive en `crates/test/src/test262.rs`. Lee el frontmatter YAML-ish de
cada test a mano (sin dependencia de `serde_yaml`), arma el harness (`assert.js`,
`sta.js`, `includes`, `$262`), y lo corre contra `vvva_js::JsEngine`.

### Módulos ES (`flags: [module]`)

3va no usa `v8::Module` nativo — los módulos se ejecutan vía el pipeline
existente de `transpiler::transpile_to_cjs` + `require()`. Esto cubre bien
import/export básico, bindings, namespace objects, pero **no puede** replicar
fielmente la semántica de "early errors" de linking entre módulos (bindings
duplicados vía `export *`, ciclos de importación, etc.) — eso requeriría
`v8::Module` real. Los fallos en esa categoría son reales y se reportan tal
cual (no se esconden con skip) para que el número refleje la cobertura real.

## `intl402/` — en pausa deliberadamente

**Por qué:** implementar `intl402/` significa implementar el API completo de
`Intl` (ECMA-402: `Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.Collator`,
`Intl.PluralRules`, `Intl.RelativeTimeFormat`, `Intl.ListFormat`, tablas CLDR
de locales, plurales, calendarios, etc.). No es una extensión del runner de
test262 ni del `JsEngine` existente — es una superficie de API nueva del
tamaño de un proyecto aparte (típicamente resuelta con ICU embebido, que en
Rust es un dependency tree grande — `icu4x` o bindear ICU de sistema).

**Cuándo retomarlo:** si 3va necesita exponer `Intl.*` como feature de
runtime por sí misma (no solo para pasar test262), en ese momento
`intl402/` se vuelve la suite de verificación natural para esa
implementación. Hasta entonces, correr el runner de test262 simplemente no
apunta a esa carpeta (`run_suite(root, "language", ...)` /
`run_suite(root, "built-ins", ...)` — `intl402` nunca se incluye).

**Cómo retomarlo cuando toque:** implementar `Intl.*` primero como builtin
de `vvva_js` (ver `crates/js/src/builtins/` para el patrón de otros
builtins nativos), después apuntar `run_suite` a `test/intl402` y usar los
fallos como lista de trabajo — igual que se hizo con async y módulos.

## Huecos conocidos fuera de `intl402`

- **`$262.createRealm`** — necesita que `JsEngine` exponga crear un
  `v8::Context` nuevo dentro del mismo isolate.
- **`$262.agent`** — necesita hilos reales + `SharedArrayBuffer` compartido
  entre isolates (cada agente es su propio isolate, ya que `v8::Isolate`
  no es `Send`).

## Notas del motor que salieron de este trabajo

- `JsEngine::eval()` ahora usa `v8::TryCatch` y devuelve el error real de V8
  con fase: `"[parse] SyntaxError: ..."` o `"[runtime] TypeError: ..."`. Antes
  devolvía strings genéricos (`"compile error"` / `"execution error"`) sin el
  mensaje real — esto mejora los errores reportados en todo el motor, no solo
  en test262.
- `JsEngine::pump_timers()` — `idle()` solo drena microtasks y tareas de
  platform de V8, nunca avanza la rueda de `setTimeout`/`setInterval`. Un
  loop de test (o cualquier consumidor que necesite esperar timers reales)
  debe llamar `pump_timers()` explícitamente.
